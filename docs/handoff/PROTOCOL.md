# SERVISIUM — протокол співпраці агентів (ChatGPT ↔ Claude)

Версія 1.0 · 14.10.2026 · Статус: **чернетка до схвалення власником** (PR #1).

Мета — швидше й безпечніше розвивати продукт. Документи не замінюють тестування:
завдання без перевіреного результату не вважається виконаним.

## 1. Ролі

| Хто | Відповідає за | Не робить |
|---|---|---|
| **Власник (Ян)** | пріоритети, дозволи, рішення щодо даних і грошей, злиття PR, випуск у `main` | — |
| **ChatGPT** | координація черги, аналіз, постановка завдань за шаблоном, рев'ю PR, перевірка доказів | не зливає PR, не змінює Supabase |
| **Claude** | аналіз коду, реалізація погоджених завдань, тести, документування результату | не бере непогоджені завдання, не зливає PR, не змінює Supabase без дозволу |

## 2. Джерела правди

1. **GitHub** (`br7ypvzhsz-star/servisium`) — єдине спільне джерело. Агенти не бачать чатів одне одного:
   усе, що має знати інший агент, записується в репозиторій (файл завдання, PR, коментар).
2. Робоча гілка: `hardening/security-mobile`. `main` = живий сайт (GitHub Pages).
3. Стан продукту — `docs/MASTER_TASKS.md` (статуси DONE/PARTIAL/TODO/BLOCKED/UNVERIFIED з доказами).
   Історія — `docs/CHANGELOG.md`. Продовження роботи — `docs/NEXT_STEPS.md`.
   `docs/AUDIT_REPORT.md` — знімок станом на 13.10.2026, частково застарів (див. QUEUE, D-01).
4. Черга роботи — `docs/handoff/QUEUE.md`. Опис конкретного завдання — `docs/handoff/tasks/Q-xxx.md`
   за шаблоном `TASK_TEMPLATE.md`.
5. Якщо документи суперечать одне одному — правду визначає код і живий доказ, а не документ.
   Розбіжність записується в QUEUE і виправляється окремим завданням.

## 3. Життєвий цикл завдання

```
new → approved → in_progress → review → done
              ↘ blocked (потрібен дозвіл / дані / рішення власника)
```

1. **new** — завдання є в QUEUE, але не погоджене. Брати в роботу заборонено.
2. **approved** — власник погодив (у чаті або коментарем у GitHub). У файлі завдання вказано, хто й коли погодив.
3. **in_progress** — виконавець створив гілку і **чернетку PR** з ID завдання в назві. Чернетка PR = «зайнято».
4. **review** — PR переведено з чернетки; в описі є результат, тести, докази. Інший агент робить рев'ю.
5. **done** — власник злив PR, `MASTER_TASKS.md` і `CHANGELOG.md` оновлено в тому ж PR.

## 4. Гілки та Pull Request

- Одне завдання = одна гілка = один виконавець = один PR.
- Назви гілок: `claude/Q-xxx-коротко`, `chatgpt/Q-xxx-коротко`. Базова гілка — актуальна `hardening/security-mobile`.
- PR відкривається **в `hardening/security-mobile`**, ніколи напряму в `main`.
- Перед створенням гілки і перед переведенням PR у review: `git fetch` і rebase на свіжу `hardening/security-mobile`.
- PR має бути малим і стосуватися одного завдання. Не змішувати рефакторинг з функціональною зміною.
- Опис PR: ID завдання, що змінено, як перевірено (команди/кроки і їх результат), що НЕ перевірено, ризики, відкат.

## 5. Заборони (без винятків, якщо власник окремо не дозволив)

1. **Злиття в `main`** — лише власник. Автоматичне злиття, auto-merge, force-push і видалення гілок `main` / `hardening/security-mobile` заборонені.
   `main` захищений правилом «SERVISIUM - Protect Main» (лише через PR, без force-push і видалення).
2. **Злиття будь-якого PR** агентом — заборонено. Агент лише відкриває PR і робить рев'ю.
3. **Supabase** — будь-яка дія з живим проєктом `thswpihmhjychjjcybmf` потребує окремого дозволу власника
   на конкретну дію: міграції, `execute_sql` (навіть з відкатом), розгортання Edge Functions, секрети, дані, сховище.
   Важливо: тестового середовища немає. Заклад №4 — тестовий, але живе в продакшн-базі,
   тому запис туди і запуск `tests/server_suite.sql` — теж дії з живою базою.
   Файли міграцій у репозиторії можна готувати в PR; застосування — лише з дозволу.
4. **Налаштування GitHub, секрети, GitHub Actions** — лише з дозволу власника.
5. **Квота платних сервісів** (Gemini: фото-рушій, Vision-перевірки, масові AI-прогони) — лише з дозволу.
6. **Видалення даних** (дублі, фото, чеки) — лише за затвердженим правилом і з резервною копією.
7. **Вигадані дані** — не вигадувати склад, алергени, ціни, статуси. «Не підтверджено» краще за здогадку.

## 6. Секрети й персональні дані (репозиторій публічний)

- Заборонено додавати: ключі `service_role`, `GEMINI_API_KEY`, токени GitHub/Supabase, паролі, PIN, хеші PIN,
  реальні імена/телефони/email персоналу й гостей, дані чеків реальних закладів.
- Дозволено: публічний ключ Supabase (`sb_publishable_…`) у `index.html` — він публічний за призначенням і захищений RLS.
- Перед кожним PR — перевірка на секрети (§8). Якщо секрет потрапив у git — **не виправляти мовчки**:
  повідомити власника, ключ вважати скомпрометованим і замінити.

## 7. Уникнення конфліктів між агентами

1. **Захоплення завдання** — лише через чернетку PR (`[Q-xxx] …`). Немає PR — завдання вільне; є чужий PR — не чіпати.
2. **`index.html` — один файл ~10 000 рядків.** Одночасно в ньому працює лише одне завдання.
   В описі завдання вказується, які функції/розділи зачіпаються.
3. **`QUEUE.md`** змінює координатор (ChatGPT) або власник. Виконавець у своєму PR змінює лише рядок свого завдання.
4. **`CHANGELOG.md`** — нові записи лише **в кінець файлу**, заголовок `## РРРР-ММ-ДД — <опис> (Q-xxx)`.
5. **`MASTER_TASKS.md`** — змінюються лише рядки, яких стосується завдання; статус змінюється лише з доказом.
6. **Міграції** — нова міграція отримує наступний вільний номер; номер перевіряється після rebase.
7. Якщо в `hardening/security-mobile` з'явилися нові коміти — rebase перед рев'ю; конфлікт вирішує автор PR, а не рев'юер.
8. Рев'ю — коментарем у PR. Рев'юер не пушить у чужу гілку без прохання автора.

## 8. Обов'язкові перевірки перед review

Мінімум для кожного PR (не потребують доступу до Supabase):

| Перевірка | Як |
|---|---|
| Синтаксис JS у `index.html` | витягти inline-скрипти й перевірити `node`-парсером (`vm.Script`) — 0 помилок |
| Синтаксис `sw.js`, `mobile/scripts/*.mjs` | `node --check <файл>` |
| Секрети | пошук `service_role`, `sk-`, `AIza`, `ghp_`, `-----BEGIN`, JWT (`eyJ…`) у змінених файлах — 0 знахідок |
| Межі зміни | `git diff --stat` збігається з описом завдання; немає випадкових змін у чужих файлах |

Залежно від завдання (потребує дозволу, якщо торкається живої бази):

| Перевірка | Коли |
|---|---|
| `tests/server_suite.sql` (очікувано `SUITE RESULT: 41/41 passed`) | зміни SQL, RPC, політик |
| Браузерний сценарій на закладі №4 | зміни UI з записом у БД |
| Перевірка на реальному телефоні/планшеті | зміни інтерфейсу (виконує власник або за його участі) |

Чого вимагає доказ: команда/кроки, фактичний результат (числа, а не «працює»), коміт, і окремо — **що не перевірено**.
UI без збереження на сервері не вважається DONE (правило `MASTER_TASKS.md`).

## 9. Документування результату

У тому ж PR, що й зміна:
1. `docs/handoff/tasks/Q-xxx.md` — розділ «Результат» і «Перевірки».
2. `docs/MASTER_TASKS.md` — статус і доказ (лише рядки завдання).
3. `docs/CHANGELOG.md` — запис у кінці файлу.
4. `docs/handoff/QUEUE.md` — стан свого рядка (`review`).

## 10. Відомі обмеження процесу

- Агенти не мають доступу до чатів одне одного; передача — лише через GitHub.
- Немає staging-бази: перевірки SQL і запису в БД відбуваються на живому проєкті (лише з дозволом).
- PR від Claude створюються від імені акаунта власника (GitHub App), коміти — від акаунта `claude`.
  Тому обов'язкове схвалення PR на GitHub не налаштовується без блокування самого власника;
  захист `main` тримається на правилі репозиторію і забороні злиття агентами (§5).
- Автоматичний запуск агентів за розкладом ще не налаштовано (окреме рішення власника).
