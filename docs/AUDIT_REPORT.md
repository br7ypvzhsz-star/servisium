## 2. Критичні проблеми (P0)

### C1. RLS не захищає нічого — повна відсутність ізоляції тенантів
Усі 16 політик у `public` мають `USING (true)` / `WITH CHECK (true)` для ролі `anon`. Anon-ключ публічний за визначенням (він у frontend), тому **будь-хто в інтернеті може**:
- читати, змінювати й **видаляти** `restaurant_staff` (імена, email, `pin_hash`);
- читати/змінювати/створювати меню, стоп-лист, замовлення й чеки **будь-якого** ресторану;
- створювати ресторани.
`restaurant_id` присутній у таблицях, але жодна політика його не перевіряє. Security advisor показав порожній список — на ці політики він не реагує, тому **не можна вважати «advisor чистий» доказом безпеки**.

### C2. Авторизація відсутня фактично
- `auth.users` = 0: жодного адміністратора в Supabase Auth не існує, тобто «admin через Supabase Auth» зараз не працює або не використовується.
- `restaurant_staff.pin_hash` у 3/3 рядків схожий на SHA-256 (64 hex). Простір 4-значного PIN = 10 000 варіантів, а хеші публічно читаються (C1) → PIN відновлюється за секунди. `auth_user_id` не заповнений ні в кого.
- Отже, перевірка ролей/PIN, імовірно, виконується на клієнті (потребує підтвердження по коду frontend).

### C3. Edge Functions без автентифікації
`enrich-menu-photos` і `analyze-hall-ai`: `verify_jwt=false`, CORS `*`, жодної перевірки користувача чи належності `restaurant_id`. Перша працює з service-role ключем (пише у сховище), друга приймає до ~18 МБ і викликає платний Gemini. Будь-хто може спалювати квоту/гроші й засмічувати сховище. (Увага: `verify_jwt=true` сам по собі теж недостатній — anon-ключ є валідним JWT; потрібна перевірка ролі/належності до ресторану в коді.)

### C4. Повторний імпорт створює дублікати (підтверджено даними)
Ресторан «Тест»: 481 рядок при 251 унікальній парі назва+меню → ≈230 дублів. У **всіх 1351** рядків `source_id`, `source`, `menu`, `menu_id`, `category_id`, `thumbnail_url` = NULL, тому ідемпотентний імпорт технічно неможливий (немає ключа порівняння). Функція `import-menu` нічого не пише в БД — запис робить frontend.

### C5. Схема не покриває продукт
Відсутні: зали/столи, місця, інгредієнти/склад/алергени (структуровані), техкарти, чеки/архів, зміни/аналітика, навчання/тести, журнал аудиту, мульти-тенантна модель (користувач ↔ ресторан ↔ роль). `orders.table_id` без таблиці столів. `order_items` має дубльовані колонки (`qty`/`quantity`, `price`/`unit_price`).

## 3. Що реально працює (підтверджено)

- Supabase-проєкт доступний і здоровий; дані зберігаються на сервері (T022 частково ✔).
- `import-menu`: код читає лише `expz.menu` (перевірка домену → захист від SSRF); для LUGOSH у БД рівно очікувані **319 позицій = 74 кухня + 245 бар** (збігається з handoff).
- Photo Engine **не чіпав кухню**: серед 74 страв LUGOSH 0 фото з нашого сховища (59 — оригінальні фото Expz, 15 — без фото). Коктейлі, кава, води/соки, mocktails — теж 0 фото від двигуна.
- Для бару LUGOSH: 165 з 245 мають фото з нашого сховища, 46 — зовнішні (Expz), 34 — без фото. Історичне «0/319» застаріло.
- Стоп-лист: структура таблиці відповідає вимогам (причина, очікуване повернення, статус, хто створив/закрив) — 12 записів.

## 4. Що не працює / не підтверджено

- Ізоляція даних, авторизація, ролі — **не працюють** (C1–C2).
- Ідемпотентний імпорт — **не працює** (C4).
- Повне збереження полів імпорту (external ID, metadata, склад, алергени, валюта, вага/об'єм у структурі) — **не працює**.
- Якість категорій: категорії вин = країни; одна й та сама країна записана як `Italy` / `Італія` / `Італiя` (латинська `i` або `a` у кириличних словах — омогліфи), тип вина (біле/червоне/ігристе) втрачено.
- Photo Engine: код використовує функцію `similarity()`, яку я **не знайшов** у вихідному файлі; це потребує тесту виклику (при підтвердженні — функція падає на кожному елементі). У БД не зберігаються джерело, впевненість і причина відхилення (`source` = NULL), тож точність 165 фото **неперевірювана**. Перелік брендів у коді захардкоджено (15 назв).
- `analyze-hall-ai` містить захардкоджений референс залу LUGOSH (2 поверх) у системному промпті для всіх ресторанів — порушення мульти-тенантності; regex `isSecondFloorReference` з подвійним екрануванням працює некоректно.
- Не працюють/відсутні: наскрізний ланцюг «стіл → замовлення → чек → зміна», аналітика зміни, AI-sommelier, інгредієнти. Замовлень у БД 0.
- Frontend (UI/UX, мобільна адаптація, Master Panel, кнопка додавання ресторану, PIN-вхід) — **не перевірено**.

## 5. Що виправити першочергово (порядок)

1. **Доступ до коду frontend** (блокер) — без нього неможливо безпечно змінювати auth/RLS, бо поточний сайт працює через anon-ключ і зламається при закритті політик.
2. Бекап: дамп схеми + даних, фіксація міграцій (T002).
3. **Нова модель безпеки**: таблиці `tenant_members(user_id, restaurant_id, role)`, функція `auth.jwt()`-claims, RLS за `restaurant_id` + роллю; адмін — Supabase Auth; офіціант — PIN через Edge Function (slow-hash + rate-limit), що видає короткоживучий JWT з `restaurant_id`/`role`. Одночасно змінити frontend на новий потік.
4. Закрити Edge Functions: перевірка JWT + належності ресторану, rate-limit, ліміти розміру.
5. Імпорт: колонки `source`, `source_id`, `content_hash`, `last_seen_at` + `UNIQUE(restaurant_id, source, source_id)`; upsert замість insert; preview/diff; нормалізація категорій; очищення дублів **лише за правилом і з backup** (не видаляти без схвалення).
6. Схема: зали/столи, інгредієнти/алергени, чеки, зміни, audit_log.
7. Photo Engine: тест `similarity()`, журнал рішень, повний прогін 319 з доказом незмінності кухні.
8. Order flow E2E → аналітика зміни → pairing → hall AI → mobile.

## 7. Мобільні платформи (рішення)

Frontend — один статичний HTML на GitHub Pages. Найкоротший надійний шлях: (1) responsive + **PWA** (manifest, service worker, офлайн-кеш меню/залу, встановлення на екран), (2) обгортка **Capacitor** для iOS/Android з тим самим кодом, (3) публікація. Публікацію не починати до проходження безпеки й E2E-тестів. Для магазинів знадобляться: Apple Developer Program, Google Play Console, підписні ключі, privacy policy URL.
